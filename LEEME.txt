PROTECTORA DE ANIMALES - Manual de la aplicación
=================================================

1. QUÉ ES
---------
Aplicación de consola para gestionar una protectora de animales: sus animales, las
personas que quieren adoptar y las adopciones. Cada adopción se lleva un animal, que
deja de estar disponible; si lo devuelven, vuelve a estarlo.

Las tres tablas:

  animales
      id, nombre (no se repite), especie, edad, disponible (1 = sí, 0 = ya adoptado)

  adoptantes  
      id, nombre, correo (no se repite)

  adopciones  
      id, adoptante_id(adoptantes), animal_id(animales),
       devuelto (0 = lo tiene, 1 = ya lo ha devuelto)

Relacion Many2Many entre adoptantes y animales, Un adoptante puede adoptar varios animales
  y un animal puede ser adoptado por varias personas (siempre y cuando lo devuelvan antes)

2. REQUISITOS Y MODO DE ARRANQUE
--------------------------------
Python 3.12
tres librerías:
      -pgserver: descarga y arranca el servidor PostgreSQL local sin instalarlo aparte.
      -psycopg: Conecta Python con PostgreSQL para que se comuniquen.
      -sqlalchemy: el ORM, para trabajar con las tablas como objetos de Python en vez de SQL.

Para instalarlas: python -m pip install pgserver "psycopg[binary,pool]" sqlalchemy

(Si python abre la Microsoft Store, usad  py  en lugar de  python.)
La carpeta debe estar fuera de OneDrive.

Se arranca desde la terminal, dentro de la carpeta del trabajo:

    python menu.py

La primera vez, usad la opción 1 para importar los datos de partida.

3. DÓNDE GUARDA CADA COSA
-------------------------
  protectora.db          La base SQLite (un fichero). Se crea al arrancar.
  pgdatos/               El servidor PostgreSQL. Se crea sola con la opción 10
                         (se puede borrar, se vuelve a crear).
  datos/animales.csv     Los animales con los que se empieza (nombre;especie;edad).
  datos/adoptantes.csv   Los adoptantes con los que se empieza (nombre;correo).
  datos/registro.txt     El registro: una línea con fecha y hora por cada operación.
  datos/informe.json     El informe de adopciones por especie (opción 7).
  datos/informe.xml      El mismo informe en XML (opción 16).
  datos/adopciones_adoptante_N.csv
                         Las adopciones de un adoptante, para abrir en una hoja de
                         cálculo (opción 12).
  copias/                Las copias de seguridad de la base (opción 17).

Los CSV van separados por ";" y están guardados en UTF-8

Ficheros del programa:
  menu.py       El menú y todo el SQL a mano (sqlite3).
  ficheros.py   Registro, JSON, XML y copia de seguridad.
  orm.py        Lo que se hace con el ORM (SQLAlchemy).
  servidor.py   Lo que se hace en PostgreSQL.

4. CÓMO SE USA
--------------
Se escribe el número de la opción y Intro. Si algo sale mal, la aplicación lo dice con
un mensaje y vuelve al menú; no se cierra.

 1. Importar los datos de partida (CSV)
      Lee datos/adoptantes.csv y datos/animales.csv y mete cada fila. 
      Se puede repetir, lo que ya está no se duplica y lo demás se importa.

 2. Ver o buscar animales
      Busca por nombre o por especie, sin diferenciar entre MAYUSCULAS y minusculas.
      Con Intro se ven todos.

 3. Alta de un animal
      Pide nombre, especie y edad y devuelve su ID. 
      Si el nombre ya existe o la edad es negativa, lo rechaza.

 4. Cambiar la edad de un animal
      Pide el número del animal y la edad nueva.

 5. Adoptar un animal
      Muestra y pide el número del adoptante, luego pide el del animal (se ve en la 2) 

 6. Ver las adopciones
      Una línea por adopción: número, adoptante, animal y si lo tiene o ya lo devolvió.
      Si no ha habido ninguna adopcion no mostrara nada

 7. Crear informe, y guardarlo en JSON
      Muestra cuántas adopciones ha habido por especie, de mayor a menor, y lo guarda en
      datos/informe.json.

 8. Devolver un animal (ORM)
      Pide el número de la adopción (opción 6). La adopción pasa a devuelta y el
      animal vuelve a estar disponible.

 9. Los mejores adoptantes, con SQL a mano (ORM)
      Pide un mínimo de adopciones y enseña los adoptantes que llegan a él.
      Ejemplo: 2 -> solo los que han adoptado al menos dos veces.

10. Llevar los animales al servidor (PostgreSQL)
      Arranca PostgreSQL (la primera vez tarda), copia allí los animales y usa una función
      que vive en el servidor (total_disponibles) y otra (edad_media), y un procedimiento
      (cumplir_anios), que se llama con CALL. Con los datos de partida: 6 animales,
      6 disponibles, edad media 3.67 y, tras CALL cumplir_anios(1), 4.67.
      Se puede usar las veces que haga falta: vacía la tabla del servidor antes de copiar.

11. Las estrellas: el animal más adoptado y el adoptante que más adopta
      Dos consultas con LIMIT 1. Si todavía no hay adopciones, lo dice.

12. Las adopciones de un adoptante, a un CSV
      Pide el número del adoptante y guarda sus adopciones en
      datos/adopciones_adoptante_N.csv (numero;animal;devuelto), listo para la hoja de
      cálculo del cliente.

13. Las adopciones de un adoptante (ORM)
      Lo mismo que la 12 pero en pantalla y con el ORM: del adoptante a sus adopciones
      y de cada adopción a su animal.

14. Alta de un adoptante (ORM)
      Pide nombre y correo. Si el correo ya está dado de alta, lo rechaza.

15. Dar de baja un animal
      Pide el número del animal. Si tiene adopciones, no deja: "No se puede: ese animal
      tiene adopciones" (lo impide la clave ajena).

16. El informe, en XML
      El mismo informe que la 7, guardado en datos/informe.xml.

17. Copia de seguridad
      Copia protectora.db en la carpeta copias, con la fecha y la hora en el nombre.

18. El informe con el ORM, y comparar
      Calcula el informe con select() de SQLAlchemy y comprueba que sale igual que el de
      la opción 7, que usa SQL a mano.

19. Cómo busca la base las adopciones de un adoptante
      Enseña el plan de la consulta (EXPLAIN QUERY PLAN). Con el índice sale
      "SEARCH adopciones USING INDEX idx_adopciones_adoptante (adoptante_id=?)".

 0. Salir

El registro (datos/registro.txt) guarda cada operación, también las que se rechazan:

    04/11/2026 15:33:03 adoptar animal 1 (adoptante 1): Adoptado
    04/11/2026 15:33:03 adoptar animal 1 (adoptante 2): Ese animal ya no está disponible

5. LAS TABLAS Y SUS RESTRICCIONES
---------------------------------
  animales
    id          PRIMARY KEY AUTOINCREMENT: la base le da el número a cada animal.
    nombre      NOT NULL (el dato es obligatorio) y UNIQUE (no puede haber dos animales
                con el mismo nombre: así no se confunden al adoptar).
    especie     NOT NULL: es obligatoria.
    edad        NOT NULL y CHECK (edad >= 0): un animal no puede tener edad negativa.
    disponible  NOT NULL, por defecto 1, y CHECK (disponible IN (0, 1)): solo vale sí o no.

  adoptantes
    id          PRIMARY KEY AUTOINCREMENT.
    nombre      NOT NULL.
    correo      NOT NULL y UNIQUE: una persona no se da de alta dos veces.

  adopciones
    id            PRIMARY KEY AUTOINCREMENT.
    adoptante_id  NOT NULL y REFERENCES adoptantes(id): no hay adopciones de un adoptante
                  que no existe.
    animal_id     NOT NULL y REFERENCES animales(id): no hay adopciones de un animal que
                  no existe, y no se puede borrar un animal que tiene adopciones.
    devuelto      NOT NULL, por defecto 0, y CHECK (devuelto IN (0, 1)).

  Índice idx_adopciones_adoptante sobre adopciones(adoptante_id): las adopciones de un
  adoptante se buscan mucho (opciones 12, 13 y 19) y así la base no recorre la tabla entera.

  En SQLite las claves ajenas no se comprueban si no se activan; por eso cada conexión
  ejecuta PRAGMA foreign_keys = ON (en menu.py y, para el ORM, en orm.py).
  Las tablas se crean con CREATE TABLE IF NOT EXISTS y sin DROP: al arrancar no se pierden
  los datos del cliente.

6. LA TRANSACCIÓN
-----------------
Adoptar (opción 5) son dos cambios que van juntos o no van:
    1. UPDATE animales SET disponible = 0   (el animal deja de estar disponible)
    2. INSERT INTO adopciones               (se apunta la adopción)
Los dos están dentro del mismo  with closing(conectar()) as cx, cx:  : si todo va bien
hace commit, y si salta un error hace rollback de todo.

Devolver (opción 8, con el ORM) también son dos: la adopción pasa a devuelta y el animal
vuelve a estar disponible. La sesión es la transacción: un solo commit para los dos.

Si falla a medias, no queda nada a medias. Ejemplo comprobado: adoptar el animal 2
(Toby) para un adoptante que no existe (el 99). El UPDATE ya se había ejecutado, pero
el INSERT lo rechaza la clave ajena; la transacción se deshace entera y Toby sigue
disponible: justo después, otro adoptante pudo adoptarlo sin problema.

7. VENTAJAS E INCONVENIENTES
----------------------------
El conector (sqlite3 y psycopg)
  - Ventaja: SQL a mano da control total. Los parámetros siempre van aparte (? en sqlite3
    y %s en psycopg), nunca pegados a la consulta, así que nadie puede colar SQL en el
    nombre de un animal o en un correo.
  - Inconveniente: el SQL se repite en muchas funciones y cada gestor tiene sus detalles
    (la marca del parámetro, los errores, cómo se conecta). Cambiar de gestor obliga a
    tocar bastante código.

El gestor embebido (SQLite) frente al que tiene servidor (PostgreSQL)
  - SQLite es un fichero (protectora.db): no hay nada que instalar ni que arrancar, y
    para una protectora con un ordenador en la oficina es suficiente. Su límite: una
    protectora con varias personas trabajando a la vez en distintos ordenadores. Tampoco
    puede guardar código dentro de la base (funciones y procedimientos).
  - PostgreSQL es un servidor: atiende a varios clientes a la vez, cada uno ve una foto
    coherente de los datos (aislamiento) y permite funciones y procedimientos en la base
    (total_disponibles, edad_media, cumplir_anios). Su coste: hay que instalarlo y
    arrancarlo (la opción 10 tarda la primera vez) y ocupa más (la carpeta pgdatos).

El ORM (SQLAlchemy) frente al SQL a mano
  - Ventaja: se trabaja con objetos (adopcion.animal.disponible = True) y no se escribe
    SQL para lo normal; detecta los cambios solo y la sesión hace de transacción.
  - Inconveniente: hay que aprender sus clases y se pierde de vista qué SQL se ejecuta
    (sin selectinload, recorrer las adopciones de un adoptante lanzaría una consulta por
    cada animal: el problema N+1). Para los informes con agrupaciones, el SQL a mano
    sigue siendo más directo (por eso la opción 9 usa text() dentro de la sesión).
  - No es "ORM o SQL": ORM para lo normal y SQL a mano donde haga falta.

8. CÓMO SE LEEN LOS FICHEROS
----------------------------
El CSV de partida y el registro son ficheros de texto con líneas de distinta longitud: se
leen de principio a fin, línea a línea (acceso secuencial). Es lo adecuado aquí, porque
siempre se necesitan todas las líneas (importar) o solo se añade al final (registro).

Un fichero de registros de tamaño fijo (cada animal ocupando, por ejemplo, 20 bytes)
se podría leer por su posición con seek(), sin recorrer lo anterior (acceso aleatorio,
ejemplo 11): el animal número 4 está en el byte 4 x 20. Nos convendría si la protectora
tuviera miles de fichas y hubiera que consultar o cambiar una concreta con frecuencia sin
leerlas todas. Con unos pocos animales y con la base de datos, que ya hace eso mejor
(índices), no compensa.

9. CÓMO LO HEMOS PROBADO
------------------------
Pruebas hechas a propósito (menu.py con base nueva). Cada una da su mensaje, sin Traceback.

  Opción que no existe (77)                  -> Esa opción no existe
  Letras donde va un número (opción 5, "abc")-> Eso no es un número
  Dato repetido (alta de "Luna")             -> No se puede: UNIQUE constraint failed: animales.nombre
  Correo repetido (opción 14)                -> pendiente (ver más abajo)
  Número negativo (alta con edad -1)         -> No se puede: CHECK constraint failed: edad >= 0
  Número negativo (cambiar edad a -3)        -> No se puede: CHECK constraint failed: edad >= 0
  Nombre vacío (opción 3)                    -> El nombre y la especie son obligatorios
  Animal que no existe en la 4               -> Ese animal no existe
  Animal que no existe en la 5               -> Ese animal no existe
  Adoptante que no existe en la 5            -> Rechazado: FOREIGN KEY constraint failed
  Adoptante que no existe en la 12           -> Ese adoptante no existe
  Animal que ya no está disponible (la 5)    -> Ese animal ya no está disponible
  Dar de baja un animal con adopciones       -> No se puede: ese animal tiene adopciones
  Dar de baja un animal que no existe        -> Ese animal no existe
  Importar dos veces                         -> "no entra (UNIQUE constraint failed: ...)" en
                                                cada línea y "0 filas nuevas": no duplica nada
  CSV sin el fichero (renombrado)            -> Falta el fichero datos/animales.csv
  CSV con una línea sin el ;                 -> adoptantes.csv, línea 2: viene mal, la salto
  CSV con letras en la edad                  -> animales.csv, línea 2: viene mal, la salto
  CSV con edad negativa                      -> animales.csv, línea 3: no entra (CHECK constraint failed: edad >= 0)
  CSV guardado en ANSI (sin UTF-8)           -> animales.csv no está guardado en UTF-8: guardadlo de nuevo desde VS Code

  El plan de la opción 19:
    Antes de crear el índice:  SCAN adopciones
    Con el índice:             SEARCH adopciones USING INDEX idx_adopciones_adoptante (adoptante_id=?)
